## 三、缺陷清单与修复

### F-01【P0】数值 ID 缺少范围约束 → PostgreSQL 22003 → 兜底 500

#### 问题现象

三条路径在传入超大整数时稳定返回 HTTP 500，并在日志中落一条 ERROR：

| 请求 | 修复前 |
|---|---:|
| `GET /api/replay/99999999999999999999` | **500** |
| `GET /api/blind/99999999999999999999` | **500** |
| `GET /api/replay/compare?startSeq=99999999999999999999&endSeq=...` | **500** |
| `POST /api/challenge/join` body `{"sessionId":99999999999999999999,...}` | **500** |

日志原文（截取关键字段）：

```json
{"level":"ERROR","msg":"请求未捕获异常","path":"/api/replay/99999999999999999999",
 "err":{"code":"22003","message":"value \"100000000000000000000\" is out of range for type bigint",
 "stack":"...\n at async getSession (.../replayService.js:393:20)\n at async file:///app/src/routes/replay.js:74:14"}}
```

```json
{"level":"ERROR","msg":"请求未捕获异常","path":"/api/challenge/join",
 "err":{"code":"22003","message":"value \"100000000000000000000\" is out of range for type integer",
 "stack":"...\n at async joinChallenge (.../dailyChallengeService.js:227:20)"}}
```

即：**用户（或扫描器）只需在地址栏把 ID 改成一个大数，就能制造服务端 5xx 告警**，
污染 5xx 指标、掩盖真实故障，并可被用作低成本的日志噪声攻击。

#### 根因分析

四处调用点都用 `Number.isInteger(x)` 做「是不是整数」的校验，但该 API **只判断整数性，不做范围约束**：

```js
Number.isInteger(1e20)   // => true   ← 顺利通过校验
Number('99999999999999999999') // => 1e20
```

`1e20` 远超 PostgreSQL `bigint` 上限 `9223372036854775807`，更远超 `integer`（int4）上限 `2147483647`。
校验放行后该值原样下发 SQL，数据库拒绝解析，抛 **22003**，被 `errorHandler` 兜成统一的 500。

这类缺陷此前已在前几轮针对 `NaN`（22P02）修过一版 `parseIdParam`，但**只补了「非数字」、漏了「超出范围的合法整数」**，
因此是一个遗留的同一缺陷类的**横向变种**。

> ⚠️ 排查要点：`/api/blind/...` 与 `/api/replay/...` 命中 **bigint** 列，而 `/api/replay/compare`、
> `/api/challenge/join` 命中 **integer** 列。库里 int4 / int8 **混用**，
> 因此仅加 `Number.isSafeInteger`（上限 2^53-1）**不足以修复全部**，必须对 int4 上下界收敛。

#### 涉及文件与代码位置

| # | 文件 | 位置 | 原写法 | 命中列类型 |
|---|---|---|---|---|
| 1 | `backend/src/middleware.js` | `parseIdParam()` L193 | `Number.isInteger(n) && n > 0` | bigint（经 9 处 blind 路由 + 4 处 replay 路由 + orders + rooms 间接触发） |
| 2 | `backend/src/routes/replay.js` | `/replay/compare` L58-62 | `Number.isInteger(startSeq)` | **integer** |
| 3 | `backend/src/routes/challenge.js` | `/challenge/join` L55 | `Number.isInteger(sessionId) \|\| sessionId <= 0` | **integer** |
| 4 | `backend/src/utils/num.js` | — | 无可用判定工具 | — |

#### 具体修改措施

采用「**单一边界 + 复用既有守卫**」的策略，不新增概念、不改调用方契约：

1. **`backend/src/utils/num.js`（新增导出）**
   - `INT32_MAX = 2147483647`：int4 上限常量，附注释说明本库 int4/int8 混用、须取更严格的一侧。
   - `isDbInt(v)`：判断值能否安全写入 PostgreSQL `integer` 列（`Number.isSafeInteger(v) && |v| <= INT32_MAX`）。
     与既有 `clampInt` 分工明确：`clampInt` 用于**夹取**（分页/限流），`isDbInt` 用于**判定**
     （ID/序号这类必须原样匹配的入参，夹取会查到错误的行，只能拒绝）。

2. **`backend/src/middleware.js` · `parseIdParam()`**（一处修复覆盖全部 16 个现存调用点）

   ```js
   // 修复前
   return Number.isInteger(n) && n > 0 ? n : null;
   // 修复后
   return Number.isSafeInteger(n) && n > 0 && n <= INT32_MAX ? n : null;
   ```

   上界取 int4 上限而非 `MAX_SAFE_INTEGER`：它同时满足 int4 与 int8，一次性消灭整个缺陷类；
   而真实表行数远低于 2147483647，不会误伤任何合法 ID。

3. **`backend/src/routes/replay.js` · `/replay/compare`**

   ```js
   // 修复前
   if (!Number.isInteger(startSeq) || !Number.isInteger(endSeq)) {
   // 修复后
   if (!isDbInt(startSeq) || !isDbInt(endSeq)) {
   ```

   保持原有的「非整数 → 400 区间参数错误」语义不变，只额外拒绝越界值。
   刻意**不**改用 `parseIdParam`：后者要求 `> 0`，而现有逻辑允许 0，改了会缩小合法输入范围。

4. **`backend/src/routes/challenge.js` · `/challenge/join`**

   ```js
   // 修复前
   const sessionId = Number(req.body?.sessionId);
   if (!Number.isInteger(sessionId) || sessionId <= 0) throw businessError('训练 ID 无效', 400);
   // 修复后
   const sessionId = parseIdParam(req.body?.sessionId);
   if (sessionId === null) throw businessError('训练 ID 无效', 400);
   ```

   改为复用 `parseIdParam`，与其余 `:id` 路由统一口径（该函数本就要求 `> 0`，语义完全等价）。

5. **回归测试**：新增 `backend/tests/unit/parseIdParam.test.js`（9 例）+ 复用既有 `numParam.test.js`（9 例）。

#### 兼容性说明

- 对**所有合法输入**（真实 ID、区间 seq 典型值 8660/8661）的返回值与修复前**完全一致**；
- 仅把「会造成 500 的越界值」改判为 400，**不放行任何新输入**，不存在权限绕过风险；
- 未改动任何状态码语义、错误文案或既有上限值与默认值。

### F-02【P1】宿主测试进程把日志写进生产日志目录

#### 问题现象

10-29 当天生产日志 `app-2026-10-29.log` 的 WARN 中，有 **100 条堆栈路径为 `file:///D:/www/nas-claw/mm8888/...`**，
并伴随 209 条「请求被拒绝(4xx)」、100 条「业务规则拒绝(4xx)」、以及 5 条「注册失败」——
这些全部来自宿主的**测试进程**，却被写进了生产日志文件。

#### 根因分析

`docker-compose.yml`（backend.volumes）把宿主 `./backend/logs` 挂载进容器的 `/app/logs`：

```yaml
backend:
  volumes:
    - ./backend/logs:/app/logs
```

而 `logger.js` 的默认目录恰好是 `path.resolve(process.cwd(), 'logs')`：
- 容器内 `cwd=/app` → `/app/logs` → 宿主 `backend/logs`
- 宿主跑测试时 `cwd=backend` → `backend/logs`

**两侧同名 ⇒ 宿主跑一次测试，日志直接追加进当天的生产日志文件。**

该缺陷自 10-24 起连续多轮被记录为「未修」项，本次首次修复。

#### 影响

1. 生产日志被大量测试噪声淹没 —— 本次 842 条 WARN 中 314 条来自宿主，直接干扰本次错误日志分析；
2. 宿主缺少 `JWT_SECRET`，`auth.js` 打出「当前使用默认 JWT 密钥」的**假安全告警**；
3. 故障排查时极易把测试流量误判为真实用户流量。

#### 涉及文件与代码位置

`backend/src/logger.js` L13：`const LOG_DIR = process.env.LOG_DIR || path.resolve(process.cwd(), 'logs');`

#### 具体修改措施

在不改变任何生产行为的前提下做**定向隔离**。判定依据（实测 Node 20）：
`node --test` 会为测试进程注入环境变量 `NODE_TEST_CONTEXT`（实测值 `child-v8`），
生产容器不会注入该变量。

```js
function isTestRun() {
  return Boolean(process.env.NODE_TEST_CONTEXT) || process.env.NODE_ENV === 'test';
}

const LOG_DIR =
  process.env.LOG_DIR ||
  (isTestRun()
    ? path.resolve(process.cwd(), 'logs', 'test')
    : path.resolve(process.cwd(), 'logs'));
```

关键取舍：
- **显式 `LOG_DIR` 优先级保持在最前**，既有 override 行为不变；
- 生产容器实测 `NODE_ENV=production`、`NODE_TEST_CONTEXT` 为空 → 仍写 `/app/logs`，**行为零变化**；
- 未改动 npm 脚本，避免在 Windows 下引入 `cross-env` 之类的新依赖。
