## 4. 修复项

### F-01（P1）Docker daemon 重启后生产不自愈，日志断档

**问题现象**

- 本轮启动排查时，`backend/logs/` 下**没有 `app-2026-11-03.log`**，最新日志停在 11-02 21:09:41。
- `docker ps -a` 显示 `mm8888-db-1` / `mm8888-backend-1` / `mm8888-frontend-1` 均为
  `Exited (0) 4 hours ago`，`FinishedAt = 2026-11-02T13:09:41Z`（= 上海 21:09）。
- 同一台宿主机上 `zzmei-*` / `brush-*` / `lnmp-*` 等容器在 Docker Desktop 重启后**全部自动 Up**，
  只有 mm8888 三个容器停在 Exited —— 说明不是「Docker 没起来」，而是本项目服务的重启策略不生效。
- 后果：`http://localhost:8080` 不可达；日志出现 4 小时空洞，**「无 ERROR」实为「服务没在跑」**，
  会直接误导任何基于日志的故障分析（包括本自动化任务本身）。

**根因分析**

1. `docker-compose.yml` 三个服务均为 `restart: unless-stopped`。
2. Docker Desktop 关闭时向容器发 `SIGTERM`；`backend/src/logger.js:200-223` 的
   `installProcessGuards()` 捕获信号执行优雅关闭并 `process.exit(0)`（`ExitCode=0` 与之吻合）。
3. Desktop 关闭/重启会把这批容器记为「已停止」，`unless-stopped` 的语义是
   「除非被显式停止，否则重启」——被标记停止后 daemon 恢复时**不再拉起**。
4. 对照：同机其他项目均为 `restart: always`（`docker inspect` 实测），daemon 恢复后无条件拉起，故全部自动恢复。

**涉及文件与代码位置**

| 文件 | 位置 | 内容 |
| --- | --- | --- |
| `docker-compose.yml` | 第 4 行（`db`）、第 22 行（`backend`）、第 73 行（`frontend`） | `restart: unless-stopped` |
| `backend/src/logger.js` | 第 200–223 行 `installProcessGuards()` | SIGTERM → 优雅关闭 → `process.exit(0)`（解释 `ExitCode=0`，本身不是缺陷，无需改） |
| `backend/src/index.js` | 第 66 行附近 | 业务中间件挂载（与本次修复无关，仅用于定位） |

**具体修改措施**

1. `docker-compose.yml`：三处 `restart: unless-stopped` → `restart: always`；
   在 `db` 段补注释记录证据链与决策理由（避免后人改回）。
2. 对运行中的三个容器执行 `docker update --restart=always`，**立即生效、不重建容器、不中断服务**；
   `docker-compose config` 确认下次 `up -d --build` 会从 compose 文件继承 `always`。
3. 未改动任何业务代码、未改 `logger.js` 的优雅关闭逻辑 —— 符合「不破坏现有功能」。

**方案对比与选型理由**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A. `restart: always`（采用）** | 与同机其他项目一致；daemon 恢复无条件拉起；零新增组件、改 3 行 | 手动 `docker stop` 后若 daemon 再重启，容器会被重新拉起（需运维知悉） | ✅ 采用 |
| B. 保留 `unless-stopped` + 外部守护脚本/开机自启 | 语义更「尊重手动停止」 | 引入额外进程与维护面，单机场景过度设计 | ❌ |
| C. 只加停摆告警 | 不改配置 | 治标：故障时仍不可用，且告警通道本身也需维护 | ❌ |

**已知风险（显式列出）**

- `always` 策略下，若运维手动 `docker stop` 后 Docker daemon 再次重启，容器会被自动拉起。
  本项目为单机常驻服务，历史发布工作流是 `git commit → git push → docker-compose up -d --build`，
  不使用「手动 stop 保持停机」这一操作，故风险可接受；如未来需要计划性停机，应改用 `docker-compose down`
  （会移除容器，`always` 不会自动重建）。
- **未实际重启 Docker Desktop / daemon 做端到端复验**：会中断同机其他项目的线上容器，代价过大。
  验证依据为「同机 `always` 容器的对照行为」+「`docker-compose config` 渲染」+「`docker update` 运行时生效」三者。
