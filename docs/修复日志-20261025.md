## 四、逐条详解

### F-01 · 回放路由 `:id` 未校验导致 500（本次新发现并修复）— **P0**

**问题现象**

生产日志（10-25 01:04，本次主动复现）：

```
ERROR 请求未捕获异常  {"path":"/api/replay/abc/step",  "err":{"code":"22P02","message":"invalid input syntax for type bigint: \"NaN\""}}
ERROR 请求未捕获异常  {"path":"/api/replay/abc/trade", "err":{"code":"22P02","message":"invalid input syntax for type bigint: \"NaN\""}}
ERROR 请求未捕获异常  {"path":"/api/replay/abc/finish","err":{"code":"22P02","message":"invalid input syntax for type bigint: \"NaN\""}}
ERROR 请求处理失败(5xx) {"status":500}
ERROR 请求未捕获异常  {"path":"/api/replay/1.5/step",  "err":{"code":"22P02","message":"invalid input syntax for type bigint: \"1.5\""}}
```

任何人在路径里填非数字（或小数）就能让服务端报 500 并污染 5xx 指标。

**根因分析**

1. 路由里直接 `Number(req.params.id)`：`'abc'` → `NaN`，`'1.5'` → `1.5`；
2. 该值作为 `$1` 传给 pg，pg 把它序列化成字面量 `'NaN'` / `1.5`；
3. PostgreSQL 解析 `bigint` 列失败，抛 **22P02**；
4. `errorHandler` 兜底 → **500 + ERROR 日志**。

同一个 bug 类在 `GET /api/replay/:id` 上有一道弱校验（`Number.isInteger`），
但 **`step` / `trade` / `finish` 三个 POST 完全没有校验** —— 属于 10-24 修复 `orders`/`rooms` 时的漏网。
且弱校验会放行 `0` 和负数，虽然只返回 404，但与 `parseIdParam` 口径不一致。

**涉及文件与代码位置**

| 文件 | 位置（改动后行号） |
|---|---|
| `backend/src/routes/replay.js` | `import` 第 5 行 |
| `backend/src/routes/replay.js` | `GET /replay/:id` → 第 72–74 行 |
| `backend/src/routes/replay.js` | `POST /replay/:id/step` → 第 89–91 行 |
| `backend/src/routes/replay.js` | `POST /replay/:id/trade` → 第 102–104 行 |
| `backend/src/routes/replay.js` | `POST /replay/:id/finish` → 第 113–115 行 |
| 调用链（未改动） | `services/replayService.js` `getSession()` ← `stepSession/tradeInReplay/finishSession` |

**具体修改措施**

复用项目已有的 `middleware.parseIdParam()`（正整数校验，非法返回 `null`），
4 个处理器统一改为：

```js
// backend/src/routes/replay.js
import { asyncHandler, parseIdParam } from '../middleware.js';

const sessionId = parseIdParam(req.params.id);
if (sessionId === null) return res.status(400).json({ error: '会话 ID 无效' });
```

不引入新工具函数、不改 `replayService`，保持与 `orders.js` / `rooms.js` 完全一致的写法与响应文案风格。
