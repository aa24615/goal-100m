## 2. 日志条目逐条梳理

### L-01 【ERROR】 `SyntaxError: Expected property name or '}' in JSON at position 1`

| 项 | 内容 |
|---|---|
| **现象** | 日志 `{"level":"ERROR","msg":"请求未捕获异常","method":"POST","path":"/api/auth/login","body":{}}`，堆栈 `JSON.parse → body-parser`。实测该请求返回 **HTTP 500** |
| **错误类型** | 错误处理缺陷（HTTP 语义错误 + 错误分级错误） |
| **触发场景** | 客户端发送不符合 JSON 语法的请求体（报文截断、未转义、编码错误） |
| **根本原因** | `errorHandler` 对所有异常一律 `res.status(500)` 并 `logger.error()`。而 `express.json()` 解析失败时抛出的错误**自带 `err.status = 400` / `err.type = 'entity.parse.failed'`**，该属性被完全忽略 → 客户端错误被升级成服务端故障 |
| **源码位置** | `backend/src/middleware.js:77-89`（修复前） |
| **危害** | ① 客户端拿到 500，会误以为服务端挂了并可能重试，放大流量；② 污染 error 日志与告警，掩盖真实 5xx；③ `body` 为 `{}`，原始报文无法回溯 |
| **处置** | 已修复，见第 3 节 D-01 |

## 3. 修复清单

### D-01 客户端畸形报文被判为服务端 5xx 【高】

- **根因**：`errorHandler` 不识别 `express.json()` 抛出的 `err.status`
- **修改文件**：`backend/src/middleware.js:76-108`
- **修改措施**：
  1. 新增 `clientErrorStatus(err)`：读取 `err.status / err.statusCode`，仅当落在 `[400,500)` 区间才认定为客户端错误
  2. 客户端错误走 `logger.warn('请求报文非法(4xx)')` 并返回**原状态码**（400 / 413）
  3. 补充记录 `errType`（如 `entity.parse.failed`），便于定位是哪一层解析失败
  4. 真异常仍走 `logger.error('请求未捕获异常')` + 500

```js
function clientErrorStatus(err) {
  const s = Number(err?.status || err?.statusCode);
  return Number.isInteger(s) && s >= 400 && s < 500 ? s : 0;
}
```

- **验证结果**：`POST /api/auth/login` + `{bad json}` → 由 `HTTP 500` 变为 **`HTTP 400 {"error":"请求报文格式错误"}`**；日志级别由 ERROR 降为 WARN，携带 `errType=entity.parse.failed`；`error-*.log` 不再产生新条目

### D-02/D-03 反向代理下客户端 IP 记录失真 【中】

- **现象**：同一请求两处 IP 不一致
  - `requestLogger`：`192.168.96.1`（真实客户端）
  - 业务日志（`注册成功`/`登录失败` 等）：`::ffff:192.168.96.4`（nginx 容器网关地址）
- **根因**：未启用 `trust proxy`，Express 的 `req.ip` 退化为 socket 对端地址；同时 `clientIp()` 直接取 `X-Forwarded-For` **首位**，该值可被伪造
- **修改文件**：`backend/src/index.js:21-24`、`backend/src/middleware.js:26-30`
- **修改措施**：
  1. `app.set('trust proxy', 1)` —— 只信任最后 1 跳，**不设 `true`**（否则可被伪造 XFF 首位）
  2. `clientIp()` 改为优先返回 `req.ip`（已由 trust proxy 按信任跳数解析出真实客户端）

- **验证结果**：业务日志与请求日志 IP 统一为 `192.168.96.1`；伪造 `X-Forwarded-For: 1.2.3.4` 时不再被采信

### D-04 `/api/equity` 缺 `gran` 字段且静默忽略请求参数 【中】

- **现象**：前端以 `GET /api/equity?days=1&gran=minute` 请求今日分时，接口返回 `200` 但**实际返回 30 天日线**；响应体无 `gran` 字段
- **根因**：
  1. `days` 白名单为 `[7,30,90,365,0]`，`days=1` 不在其中 → 静默退回 30
  2. `gran` 参数从未解析
  3. 前端类型 `EquityResponse.gran: 'day' | 'minute'` 为**必填**，后端从不返回 → 契约违约，前端 `今日分时` 标题与说明永远不生效
- **修改文件**：`backend/src/routes/equity.js`（重写）、`frontend/src/components/EquityChart.tsx:29-32`
- **修改措施**：
  1. 解析 `gran`，契约外取值一律降级为 `day`
  2. 新增**分钟粒度分支**：按 `date_trunc('minute', created_at AT TIME ZONE 'Asia/Shanghai')` 聚合当日 `asset_snapshots`（快照每分钟写入一次），`DISTINCT ON` 取每分钟最后一条
  3. 两种粒度均回传 `gran` 字段
  4. 重构出 `point()` / `summarize()`，日线与分时共用回撤计算，日线逻辑保持与原有行为一致
  5. 实时点若与当分钟末快照标签相同则**覆盖**而非追加，避免重复横坐标
  6. 前端坐标轴 formatter 区分「日期 / 日期+时间」两种标签

- **验证结果**：
  | 请求 | gran | 结果 |
  |---|---|---|
  | `/api/equity?days=30` | `day` | 正常日线 |
  | `/api/equity?days=1&gran=minute` | `minute` | 返回分时点，随快照增长（观测到 3 点且无重复标签） |
  | `/api/equity?gran=hour` | `day` | 未知粒度安全降级 |
  | `/api/equity` | `day` | 默认日线 |

### D-05 日志 meta JSON 多出一个 `}` 【中】

- **现象**：控制台每行 meta 结尾为 `...}}`，如 `行情加载完成 {"stocks":28}}`
- **根因**：`emit()` 中模板字符串多写了一个闭合花括号
- **修改文件**：`backend/src/logger.js:147-150`
- **修改前**：`` ` ${JSON.stringify(...)}`} ``
- **修改后**：`` ` ${JSON.stringify(...)}` ``
- **验证结果**：控制台输出恢复为合法 JSON：`行情加载完成 {"count":28}`

### D-06 日志时间戳与文件名跨日错位 【中】

- **现象**：`app-2026-10-21.log` 中的条目 `ts` 为 `2026-10-20T17:04:54.155Z`
- **根因**：文件名与控制台用**本地时区**（容器 `TZ=Asia/Shanghai`），而 `entry.ts` 用 `new Date().toISOString()` 输出 **UTC** → 同一事件两处时间不同，且东八区每日 08:00 前文件名与 `ts` 日期必然差一天
- **修改文件**：`backend/src/logger.js:40-51, 133-136`
- **修改措施**：新增 `tzOffset()` / `localIso()`，日志条目增加 **`tsLocal`** 字段（带本地偏移，与文件名同日），保留 `ts` 为 UTC ISO 以维持机器可读性；`tsLocal` 加入 `SKIP_KEYS` 避免控制台重复输出
- **验证结果**：`{"ts":"2026-10-20T17:15:31.338Z","tsLocal":"2026-10-21T01:15:31.338+08:00",...}`，`tsLocal` 与文件名 `app-2026-10-21.log` 一致

---

### D-07 卖出路径持仓行未加锁 【低，经验证当前不可利用】

- **复核结论（重要）**：历史评审记录称此处存在"超卖竞态"。本次实测复核发现 **当前不可利用** —— 每笔交易在事务开头已执行 `SELECT cash FROM users WHERE id=$1 FOR UPDATE`（`trade.js:151`），**同一用户的所有交易被用户行锁串行化**，第二个事务在获锁后会重读到已提交的持仓余额。
- **修改文件**：`backend/src/routes/trade.js:176, 218`
- **修改措施**：买入、卖出两处持仓读取均补 `FOR UPDATE`，作为**防御性加固**（防止将来有人移除用户行锁或新增改持仓的入口）
- **风险评估**：加锁顺序恒为 `users → holdings`，不会产生死锁
- **验证结果**：买入/卖出主流程回归通过

### 5.2 缺失信息说明

1. **日志跨度不足**：可用日志仅覆盖 **2 天**（10-20 起），且日志系统本身是 10-20 才引入，无法做错误率趋势与长周期复查。
2. **前端运行时错误零采集**：浏览器 `console.error` / `window.onerror` 未上报，前端异常完全不可见 —— 本次结论仅覆盖服务端。
3. **nginx 层拒绝无应用日志**：`413` 等被 nginx 直接拦截的请求不产生任何应用日志（L-10），本次**未修**（需改 `nginx.conf` 加 `error_page` 或调整 `client_max_body_size`）。
4. **无链路追踪/APM**：仅有单机日志文件，缺少 requestId 跨服务串联（当前 requestId 只在本服务内有效）。
5. **并行修改风险**：本次执行期间，**另一会话正在并发修改同一批文件**（`market.js` 由 4.5KB 增至 17.3KB、`routes/market.js`、`trade.js` 持续变动，新增交易时段 `TRADING/BREAK/CLOSED` 与 T+1 等逻辑）。本文档中的**行号为修复时刻取值，之后可能漂移**，请以函数/符号名为准。
