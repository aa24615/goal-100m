## 二、缺陷清单与修复

### F-01【P0】双盲训练随机抽段 SQL 列名歧义 → 500

**问题现象**
`POST /api/blind/start` 连续 10 次返回 500，服务端日志成对出现
`请求未捕获异常` + `请求处理失败(5xx)`，PG 报
`ERROR: column reference "code" is ambiguous at character 8`。
发生时间：2026-10-25 02:54（UTC 10-24 18:54），来源 `::ffff:127.0.0.1`（宿主集成测试）。

**根因分析**
`blindService.pickRandomSegment()` 的候选标的查询把 `stock_daily d` 与
`stocks s` 做 JOIN，而**两张表都存在 `code` 列**。原 SQL 在 `SELECT` /
`GROUP BY` 中裸写 `code`、`name`，PostgreSQL 无法判定归属，直接抛 42702。
业务侧没有任何兜底，异常一路冒泡到 `errorHandler`，被判定为服务端故障 → 500。

**涉及文件与代码位置**
- `backend/src/services/blindService.js` → `pickRandomSegment()`，候选池查询
  （两处：主查询与「流动性门槛退化」兜底查询）
- 调用链：`routes/blind.js` `POST /blind/start` → `startBlind()` → `pickRandomSegment()`

**具体修改措施**
两处查询统一加表别名限定，并补充退化路径：

```sql
SELECT d.code AS code, s.name AS name, COUNT(*)::int AS cnt,
       MIN(d.seq)::int AS minseq, MAX(d.seq)::int AS maxseq,
       AVG(d.amount)::float AS avg_amount
  FROM stock_daily d
  JOIN stocks s ON s.code = d.code
 WHERE s.trade_status = 'NORMAL'
 GROUP BY d.code, s.name
HAVING COUNT(*) >= $1
```

同时在源码中固化注释，说明「不限定别名会让 PG 报 42702 并最终变成 500」，
避免后续改动再次踩坑。另将「数据不足」这类可预期失败改为抛
`blindError(..., 400)`，使其落入「业务规则拒绝(4xx)」而非 5xx。

**验证结果**
- ✅ `POST /api/blind/start {"bars":30}` → **HTTP 200**，返回
  `{"id":1,"alias":"标的 #9366","status":"RUNNING","totalBars":30,"decisionInterval":10}`
- ✅ PG 侧 42702 不再复现
- ✅ 测试会话已从 `blind_sessions` 清理（`remain = 0`）

### F-04【P1】业务规则拒绝被误记为「请求报文非法(4xx)」

**问题现象**
10-25 的 188 条 WARN 里有 **24 条「请求报文非法(4xx)」**，
但点开内容全是正常业务拒绝：`你不是该房间成员`、`邀请码无效`、
`仅房主可结束房间赛`、`T+1 冻结，当前可卖 0 股`、
`委托数量需为 100 的整数倍`、`剧本不存在`、`引导步序无效`。
这些与真正的报文解析失败混在一起，导致**告警分类失真、无法据此判断接口契约是否被破坏**。

**根因分析**
`middleware.errorHandler` 依据 `err.business` 标记分流：

```js
logger.warn(err?.business ? '业务规则拒绝(4xx)' : '请求报文非法(4xx)', meta);
```

但错误工厂打标不一致——`tradeError`、`blindError` 打了 `business = true`，
而以下 6 处**漏打**，于是业务拒绝全部掉进「请求报文非法」桶：

| 文件 | 函数/位置 |
|---|---|
| `services/replayService.js` | `replayError()` |
| `services/roomService.js` | `roomError()` |
| `services/scenarioService.js` | `getScenarioBars()` / `submitAttempt()`（各 1 处「剧本不存在」） |
| `services/onboardingService.js` | 「引导步序无效」「不支持的引导操作」 |
| `services/equityService.js` | 「用户不存在」 |
| `services/portfolioService.js` | 「用户不存在」 |

**具体修改措施**
为上述 7 处错误统一补 `e.business = true`，并加注释说明「业务规则拒绝 ≠ 报文非法」。
修改**仅影响日志分类字段，不改变 HTTP 状态码与响应体**，对现有功能零影响。

**验证结果**
- ✅ 触发 `POST /api/replay/start {"startSeq":1,"endSeq":1}` → 400，
  日志由 `请求报文非法(4xx)` 变为 **`业务规则拒绝(4xx)`**（容器内日志已核对）
- ✅ `blind/random-segment`、`blind/sessions`  likewise 归入业务拒绝

### F-05【P1】回放路由非法 `:id` → 22P02 → 500

**问题现象**
`POST /api/replay/abc/step`、`/abc/trade`、`/abc/finish`、`/1.5/step` 返回 500，
PG 报 `invalid input syntax for type bigint: "NaN"`，
调用栈 `getSession() → stepSession/tradeInReplay/finishSession`。
发生时间：2026-10-25 01:04，来源 `192.168.96.1`。

**根因分析**
`:id` 未校验即传入 SQL。`Number('abc')` → `NaN`、`Number('1.5')` → `1.5`，
进入 `bigint` 列时 PG 抛 22P02，被兜底成 500。
根因类别与 10-25 已修的 `orders`/`rooms` 完全一致，属**同类缺陷未按「缺陷类」横向排查**的遗留。

**涉及文件与代码位置**
- `backend/src/routes/replay.js` → `/replay/:id`、`/replay/:id/step`、
  `/replay/:id/trade`、`/replay/:id/finish`
- `backend/src/middleware.js:176` → `parseIdParam()`

**具体修改措施**
4 处路由统一改用 `parseIdParam(req.params.id)`，非法输入一律提前返回
`400 { error: '会话 ID 无效' }`。同时保留注释说明
「`/replay/history`、`/replay/compare` 必须排在 `/replay/:id` 之前，否则会被 `:id` 吃掉」。

**验证结果**
- ✅ `abc` / `1.5` / `-1` / `0` 四种非法 ID × 三个接口 = **12 例全部 400，无 500**
- ✅ 22P02 不再复现

   但上报链路的端到端有效性（浏览器 → `/api/analytics/error` → 入库）
