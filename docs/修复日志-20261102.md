## 4. 问题清单

### 4.1 已修复

#### F-01（P0）自由文本携带 U+0000 → PG 22021 → 兜底 500

| 项 | 内容 |
|---|---|
| **问题现象** | 客户端在任意自由文本字段里带一个 NUL 字符（`\u0000`），接口返回 `500 {"error":"服务器内部错误"}`，服务端日志记 ERROR 级「请求未捕获异常」。用户侧表现为「服务器内部错误」，排障时极易被误判为服务端故障。 |
| **复现路径** | ① `POST /api/blind/:id/decision` body `{"action":"hold","reason":"a\u0000b"}`<br>② `POST /api/watchlist` body `{"code":"600519","note":"a\u0000b"}`<br>③ `POST /api/analytics/error` body `{"kind":"error","name":"E","message":"a\u0000b","stack":"x"}` |
| **根因分析** | PostgreSQL 的 `text` / `varchar` / `jsonb` **一律不接受 U+0000**（这是 PG 的硬性约束，不是驱动或编码配置问题）。node-postgres 下发带 NUL 的参数时，PG 抛 **`22021 invalid byte sequence for encoding "UTF8": 0x00`**，该异常不是 `businessError`，被 `errorHandler` 兜成 500。<br>应用侧**完全没有对入参做字符集清洗**：`blindService.recordDecision()` 只做 `reason.trim()`、`watchlist.js` 只做 `.slice(0,500)`、`analyticsService.recordError()` 只做 `clip()` —— 三者都限长度、**不限字符**，长度守卫挡不住 NUL。 |
| **涉及文件与位置** | 触发点：`backend/src/services/blindService.js:794` `recordDecision()`（INSERT 在 810 行）<br>`backend/src/routes/watchlist.js:59` note 取值<br>`backend/src/services/analyticsService.js:175` `recordError()`<br>**修复点（新增/修改）**：<br>`backend/src/utils/text.js`（新增，`stripNul()` / `sanitizeDeep()`）<br>`backend/src/middleware.js:215` `sanitizeTextInput()`（新增）<br>`backend/src/middleware.js:4`（新增 import）<br>`backend/src/index.js:33,65`（import + 挂载） |
| **具体修改措施** | 1. 新增 `utils/text.js`：`stripNul()` 剥离 U+0000；`sanitizeDeep()` 就地深遍历对象/数组，带 **MAX_DEPTH=8 / MAX_NODES=20000** 双上限，防止清洗本身变成 CPU 攻击面，并保证循环引用时能终止。<br>2. 新增中间件 `sanitizeTextInput`，统一清洗 `req.body` / `req.query` / `req.params` 三条入参通道。<br>3. 在 `express.json()` 之后、**所有业务路由之前**挂载（`index.js:65`）。<br>4. **刻意只清 U+0000**：实测 U+0007 铃符、U+007F DEL、游离代理项、10 万字符文本 PG 均正常接受（返回 200），清洗面收窄到「必须清洗的最小集合」，才不会误伤合法输入。 |
| **验证结果** | ✅ 3 条原 500 路径全部返回 **200**。<br>✅ 落库核对：`blind_decisions.reason` 存 `ab`（len=2）、`frontend_errors.message` 存 `ab`（len=2），NUL 已被剥离。<br>✅ 回归：`{"action":"hold","reason":"正常理由"}` 200、`/api/health` 200；合法中文 / emoji / 引号 / 多行文本零变化（单测锁定）。<br>✅ 部署后（17:14 UTC 起）**新增 ERROR 0**。<br>✅ 单测 9/9 新增通过。 |

## 6. 部署策略说明（重要）

本轮**没有**采用常规的 `docker-compose up -d --build`，而是**外科式部署**：

```
docker cp src/utils/text.js      mm8888-backend-1:/app/src/utils/text.js
docker cp src/middleware.js      mm8888-backend-1:/app/src/middleware.js
docker cp src/index.js           mm8888-backend-1:/app/src/index.js
docker restart mm8888-backend-1
docker restart mm8888-frontend-1   # nginx 缓存了上游 backend 的旧 IP，不重启会全站 502
```

**理由**：工作区里有并行会话**未提交且未通过测试**的 v13 改动（U-01/U-02）。整体重建镜像会把这部分在途代码
一并推上生产，违反「不引入新缺陷」的硬约束。外科式替换只把本次 3 个文件注入容器，生产语义除本次修复外零变化。
改动已提交并双推（`0256d3f`），后续任何一次正常重建都会自动包含本修复。

## 8. 本轮方法论沉淀

1. **第 16 条：缺陷类要按「列类型」扫，不止是「数值范围」**。前几轮已覆盖 int4/int8/numeric/interval 的*范围越界*，
   本轮枚举 `information_schema` 后转向 `date/boolean/smallint/varchar(N)/jsonb`，结果发现这些列类型在**取值范围内**
   全都安全（代码里已有白名单或 clamp），真正的缺口是**字符集合法性**——一个与数值毫无关系的维度。
   **枚举列类型时不要只想着「上界」，还要想「这个类型根本不接受什么字符」。**
2. **第 17 条：先证伪再扩大修复面**。本轮实测 U+0007 / U+007F / 游离代理项 / 10 万字符文本**都不会**触发错误，
   因此把清洗面严格收窄到 U+0000。若凭直觉「顺手清掉所有控制字符」，就会引入误伤合法输入的风险。
3. **探测脚本不要 `| tail`**。本轮因 `| tail -60` 缓冲，跑了 30 分钟仍看不到任何中间输出，
   只能改从**日志文件**侧统计状态码分布来观测进度 —— 反而更可靠（日志是唯一真实记录）。
4. **后台进程会被回收**：`nohup ... &` 启动的探测在 Bash 工具调用结束后即被杀，必须用工具级 `run_in_background`。
5. **第 18 条：日志按大小轮转且只保留 5 份 —— 证据会被自己冲掉**。本轮探测产生的日志量把早期文件
   挤出保留窗口，17:09 的 4 条 500 原始记录在 20 分钟后就已不可查。**结论：发现错误后要立刻把原文摘录下来
   （本文件 §4.1 的逐条记录就是这么来的），不要指望事后回日志文件取证。**
6. **第 19 条：写探测脚本时，创建型端点必须显式剔除，不只是「不可逆」端点**。本轮只在 `DANGER` 里排除了
   reset/finish/abandon，漏了 `/api/blind/start` —— 它带非法单字段 body 时**依然会成功建会话**
   （因为非法字段被忽略、其余走默认值），结果静默新建了 6 个会话。「返回 200」不等于「没副作用」。
