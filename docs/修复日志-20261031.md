### 关键方法论发现（本轮最重要收获）

**用「不存在的资源 ID」做模糊测试，请求会在业务校验层 404 短路，永远到不了 SQL 层——
「0 个 5xx」是假阴性。**

会话（blind 7 / replay 3）后，立刻暴露出 5 个稳定复现的 500。
修正做法：探测前必须先取得合法资源句柄（创建或复用），再对其做参数攻击。

## 四、已修复缺陷

### F-01（P0）`/api/replay/start` 的 `capital` 越界 → `numeric` 溢出 → 兜底 500

#### 问题现象

```
POST /api/replay/start
{"startSeq": 8640, "endSeq": 8650, "capital": "1e20"}

HTTP 500
{"ts":"2026-10-31T01:12:29.422+08:00","level":"ERROR","msg":"请求未捕获异常",
 "err":{"code":"22003","message":"numeric field overflow",
        "stack":"... at async startSession (file:///app/src/services/replayService.js:420:20)
                     at async file:///app/src/routes/replay.js:37:15"}}
```

5 个稳定复现值：`1e20`、`Infinity`、`1e309`、`9223372036854775808`、`99999999999999999999`。

#### 根因分析

| 项 | 内容 |
|---|---|
| 缺陷类 | **入参只判「是否为正数」，不判「是否在 PostgreSQL numeric(p,s) 可表示范围内」** |
| 直接原因 | `initial_capital numeric(18,2)` 最多 16 位整数 + 2 位小数；1e20 与 Infinity 都是「数学上合法的正数」，`Number(capital) > 0` 判定通过，原样下发 SQL |
| PG 拒绝 | `22003 numeric field overflow` |
| 兜底后果 | `errorHandler` 转成 500 + 一条 ERROR 日志，污染 5xx 指标 |
| 为何此前未发现 | 前几轮的守卫（`isDbInt`/`clampLimit`）只覆盖 **int4 / bigint 整数列**，未覆盖 **numeric 金额列**——同一缺陷家族的另一变种 |

#### 涉及的文件与代码位置

| 文件 | 位置 | 修改前 |
|---|---|---|
| `backend/src/services/replayService.js` | `startSession()`，第 419 行 | `const init = Number(capital) > 0 ? Number(capital) : DEFAULT_CAPITAL;` |
| `backend/src/routes/replay.js` | 第 36–37 行 | 直接透传 `req.body.capital`（未改，责任收敛到服务层） |

#### 具体修改措施

**1）`backend/src/utils/num.js` —— 新增 numeric 列守卫（与既有 `clampInt`/`isDbInt` 同风格）：**

```js
export const MAX_MONEY_18_2 = 9999999999999999.99; // numeric(18,2)
export const MAX_MONEY_12_2 = 9999999999.99; // numeric(12,2)，价格类列

export function isDbMoney(v, max = MAX_MONEY_18_2) {
  return Number.isFinite(v) && v > 0 && v <= max;
}

export function clampMoney(raw, fallback, max = MAX_MONEY_18_2) {
  const n = Number(raw);
  return isDbMoney(n, max) ? n : fallback;
}
```

**2）`backend/src/services/replayService.js`：**

```js
// 修改前
const init = Number(capital) > 0 ? Number(capital) : DEFAULT_CAPITAL;
// 修改后
const init = clampMoney(capital, DEFAULT_CAPITAL);
```

**3）`backend/tests/unit/dbMoneyGuard.test.js`（新增，10 例）**：覆盖 P0 合法值原样通过、
P3 越界收敛、P4 脏输入降级、P5 收敛结果可直接下发 SQL。

#### 设计取舍与兼容性

| 决策 | 理由 |
|---|---|
| 沿用「非法 → 回落默认值」而非「一律 400」 | 与既有 `Number(x) \|\| fallback`、以及上一轮 `normalizeBenchmarkDays` 的降级口径一致；**合法请求结果零变化** |
| 不在 JS 侧做四舍五入 | 精度处理仍交给 PostgreSQL，避免 JS 与 PG 舍入差异 |
| 保留 `Number(true) === 1` 的既有行为 | 本轮只修「越界导致 500」，不擅自提高判定强度以免破坏兼容性 |
| 横向排查结论 | 全库 43 个 numeric 列中，外部可控写入点仅此一处：`createOrder` 有涨跌停夹取天然有上界，`account/reset` 从库内读取，`startBlind` 用固定默认资金 |
