## 三、已修复缺陷

### F-01（P0）`stopPlan` 越界写入 `numeric(12,2)` → 兜底 500

| 项 | 内容 |
| --- | --- |
| **问题现象** | `POST /api/blind/:id/decision` 携带 `stopPlan=1e20`（或 `99999999999999999999`）→ **HTTP 500**，日志落一条 `请求未捕获异常` |
| **错误码** | `22003` `numeric field overflow` |
| **触发场景** | 用户在训练页填写计划止损时输入极大数值，或客户端未做上界校验直接透传 |

**根因分析**

`blind_decisions.stop_plan` 列类型为 `numeric(12,2)`（上界 `9999999999.99`）。原写法：

```js
let stop = Number(stopPlan);
if (!Number.isFinite(stop) || stop <= 0) stop = null;   // ← 只判「是不是正数」
```

`Number.isFinite(1e20) === true` 且 `1e20 > 0`，因此 **1e20 是「数学上完全合法的正数」**，
原样下发 SQL 后被 PostgreSQL 拒绝，由 `errorHandler` 兜成 500 + 一条 ERROR 日志。

**这是 10-31 已修缺陷（`replayService` 的 `capital`，列类型 `numeric(18,2)`）的同类横向变种。**
上一轮横向排查时结论为「全库 numeric 列外部可控写入点仅此一处」——**该结论是错误的**，
漏掉了 `blind_decisions.stop_plan`。教训见第五节。

**涉及文件与代码位置**

- `backend/src/services/blindService.js:16` —— 导入补充 `isDbMoney, MAX_MONEY_12_2`
- `backend/src/services/blindService.js:781-785` —— 新增纯函数 `normalizeStopPlan()`
- `backend/src/services/blindService.js:808` —— `recordDecision()` 内改用该函数

**修改措施**

```js
// 新增：纯函数，便于单测锁定边界
export function normalizeStopPlan(raw) {
  const n = Number(raw);
  return isDbMoney(n, MAX_MONEY_12_2) ? n : null;
}

// recordDecision() 内
const stop = normalizeStopPlan(stopPlan);
```

沿用项目既有「非法入参回落」口径（与 `clampMoney` 一致）：非法值一律回落 `null`
（等价于「没写止损」），**合法值零变化**；不做四舍五入，精度仍交给 PostgreSQL；
刻意保留 `Number(true) === 1` 的既有行为，避免提高类型判定强度改变合法客户端结果。

### F-02（P0）导出接口 `limit` 夹而不整 → 兜底 500

| 项 | 内容 |
| --- | --- |
| **问题现象** | `GET /api/blind/export?limit=1.5` → **HTTP 500** |
| **错误码** | `22P02` `invalid input syntax for type bigint: "1.5"` |
| **触发场景** | 任意小数 `limit` 值（如从前端传入 `limit=1.5`、或分页计算产生小数） |

**根因分析**

`backend/src/services/dataRetentionService.js:173`（修复前行号）：

```js
const lim = Math.min(2000, Math.max(1, Number(limit) || 500));   // ← 夹了，但没取整
```

`Math.max(1, 1.5) === 1.5`，`Math.min(2000, 1.5) === 1.5` —— **只夹区间不取整**，
小数原样作为 `LIMIT $2` 的参数下发。SQL 的 `LIMIT` 只接受整数，PG 抛 22P02 并被兜成 500。

**这是 10-27 第 7 轮引入 `clampInt`（内部含 `Math.floor`）之后，v12 新代码重新手写夹取时
漏掉 `Math.floor` 造成的回归。** 同一写法在 v12 中出现了 23 处（见 F-03）。

**涉及文件与代码位置**

- `backend/src/services/dataRetentionService.js:20` —— 新增 `import { clampLimit } from '../utils/num.js';`
- `backend/src/services/dataRetentionService.js:177` —— `const lim = clampLimit(limit, 2000, 500);`

**修改措施**

复用既有 `clampLimit`（内部已 `Math.floor`），语义对合法输入完全等价：
`limit=10 → 10`、`limit=0/'abc' → 500`、`limit=1e20 → 2000`、`limit=1.5 → 1`。

### F-03（P1，潜伏）清理重复埋点的 `batch` 夹而不整

| 项 | 内容 |
| --- | --- |
| **问题现象** | `POST /api/analytics/integrity/purge?apply=1&batch=1.5` 将触发 22P02 → 500 |
| **当前状态** | **潜伏未复现**：库内 `dedupe_key` 非空行 8 条、重复组 0 组 → `removable === 0` 提前返回，DELETE 分支未被执行 |

**根因分析**

`backend/src/services/telemetryIntegrityService.js`（修复前行号 421 / 395）：

```js
const limit = Math.min(50000, Math.max(1, Number(batch) || 5000));  // → LIMIT $1
[String(d), Math.min(200, Math.max(1, Number(top) || 10))]          // → LIMIT $2
```

`batch` 经 `?batch=` **外部可控**且直接进入 `LIMIT $1`；`top` 当前仅内部调用。
二者同为「夹而不整」。

**涉及文件与代码位置**

- `backend/src/services/telemetryIntegrityService.js:25` —— 新增 `import { clampInt } from '../utils/num.js';`
- `backend/src/services/telemetryIntegrityService.js:397` —— `clampInt(top, 1, 200, 10)`
- `backend/src/services/telemetryIntegrityService.js:426` —— `clampInt(batch, 1, 50000, 5000)`

**横向排查结论（仅修真正进 SQL 的）**

全库扫描 `Math.min(N, Math.max(1, ...))` 写法共 23 处。其中 **20 处**把结果 `String(d)` 拼进
`($1 || ' days')::interval` —— `'1.5 days'::interval` 在 PostgreSQL 中是合法区间，
且外层已有 `Math.min(365, ...)` 兜住上界，**不会报错**，故本轮**刻意不改**（避免无谓行为变更）。
真正把值作为数值型 SQL 参数下发、会被 22P02 击穿的仅上述 3 处，已全部修复。

## 五、本轮方法论收获（新增 3 条，供后续复用）

**第 13 条：缺陷类要在「失效模式」维度扫，而不只是「列类型」维度。**
前几轮按列类型横扫（int4 → bigint → numeric(18,2) → interval），本轮补的却是**同一列类型里的另一种失效模式**：
`numeric(12,2)` 与 `numeric(18,2)` 是同一家族，但更重要的是 `blind_decisions.stop_plan` 这一个**写入点**被整个漏掉了。
上一轮「全库外部可控写入点仅此一处」的结论是错的 —— 因为当时只查了 `createOrder` / `account/reset` / `startBlind`
三个已知热点，**没有系统枚举所有 numeric 列的 INSERT 路径**。
正确做法：先用 `information_schema` 列出全部 numeric 列，再对每列反查 `INSERT INTO <表>` 的调用点。

**第 14 条：单字段 body 的模糊测试会在必填校验处短路，是系统性漏检。**
`diag-fuzz-v12.py` 阶段 5 提交的是 `{price: "1e20"}` 这种**只有一个键**的 body ——
缺 `code` 时路由在必填校验处就 400 了，永远到不了 SQL。
必须补「**合法基线 body + 逐字段替换成非法值**」（本轮新增 `diag-fuzz-body.py`）。
同理，基线的**字段名**必须真实：`/api/replay/:id/step` 吃的是 `action`+`seq` 而不是 `bars`，
用错字段名时所有用例都在 `"不支持的操作"` 400 处短路，`seq` 从未进过 SQL。

**第 15 条：诊断脚本本身会改生产数据，写脚本时就要设计清理条件。**
本轮代价（已全部还原）：
- 基线探测把会话 7 调成 `FINISHED`（17:06:31）；
- `/api/replay/start` 基线被反复调用，**新建 67 个回放会话**；
- `/api/watchlist` 基线往 user 3 自选股塞入 `600519`（分组 `😀`）；
- `/api/blind/:id/trade` 基线在会话 7 真实成交一笔，产生 `blind_orders id=2`。
全部按「先 `SELECT` 核对 `user_id` + `created_at` 再 `DELETE`」还原；
会话 7 已恢复 `RUNNING` 且 `cursor_seq=end_seq`。
