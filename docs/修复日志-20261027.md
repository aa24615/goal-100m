## 二、缺陷清单与修复

### F-01【P0】分页/限流参数只夹一边，负数与 Infinity 直进 SQL LIMIT → 500

**问题现象**

6 个复现路径全部返回 `500 {"error":"服务器内部错误"}`，服务端成对打印
`请求未捕获异常` + `请求处理失败(5xx)`，PostgreSQL 侧对应两类错误：

| 请求 | PG SQLSTATE | 报错 |
|---|---|---|
| `GET /api/transactions?page=-1&size=-5` | 2201W | `LIMIT must not be negative` |
| `GET /api/transactions?page=1&size=-1` | 2201W | `LIMIT must not be negative` |
| `GET /api/transactions?page=1e309&size=1e309` | 22P02 | `invalid input syntax for type bigint: "Infinity"` |
| `GET /api/analytics/errors?days=-1&limit=-3` | 2201W | `LIMIT must not be negative` |
| `GET /api/blind/history?limit=-5` | 2201W | `LIMIT must not be negative` |
| `GET /api/transactions/export?size=-5` | 2201W | `LIMIT must not be negative` |

**根因分析**

三处服务层的数值收敛都写成「只夹一边」，把另一边托付给调用方，而调用方并没有兜：

```js
// transactionService.js（修复前）
const p = Math.max(1, Number(page) || 1);   // 只有下界，没有上界
const s = Math.min(50, Number(size) || 20); // 只有上界，没有下界
```

- `s` 缺下界：`size=-5` → `Math.min(50, -5) = -5` → `LIMIT -5` → 2201W；
- `p` 缺上界：`Number('1e309') === Infinity`，`Infinity || 1` 仍为 `Infinity`，
  `OFFSET Infinity` 被 pg 序列化成字面量 `Infinity` → 22P02。

异常一路冒泡到 `errorHandler`，被判定为服务端故障兜成 **500**。即：用户在地址栏改一个
查询参数就能制造 5xx 告警，既污染 5xx 指标，也会淹没真实故障。

同一缺陷家族在此前多轮已反复出现（`22P02 bigint "NaN"` 的路径 ID、
replay 的 `:id`），本轮证明它仍未根除——只是从**路径参数**转移到了**查询参数**。

作为对照，`replayService.listSessions()` 的写法是正确的（两边都夹），所以
`/replay/history?limit=-5` 一直是 200：

```js
Math.min(100, Math.max(1, Number(limit) || 20))
```

**涉及文件与代码位置**

| 文件 | 位置 | 问题 |
|---|---|---|
| `backend/src/services/transactionService.js` | `listTransactions()` | page 无上界、size 无下界 |
| `backend/src/services/analyticsService.js` | `recentErrors()` | limit 无下界 |
| `backend/src/services/blindService.js` | `listBlindSessions()` | limit 无下界 |
| `backend/src/routes/review.js` | `/transactions/export` | size 无下界 |

**具体修改措施**

1. 新增 `backend/src/utils/num.js`（与既有 `utils/time.js` 同属无副作用工具层），
   提供唯一收敛口径：

```js
export function clampInt(raw, min, max, fallback) {
  const n = Number(raw);
  const v = Number.isFinite(n) && n !== 0 ? n : fallback;
  return Math.min(max, Math.max(min, Math.floor(v)));
}
export const clampLimit = (raw, max, fallback) => clampInt(raw, 1, max, fallback);
```

口径刻意与既有 `Number(x) || fallback` 保持一致，避免改坏现有行为：
`0 / 空串 / NaN / Infinity / null / undefined` 取 `fallback`；其余值先取整再夹到
`[min, max]`，负值夹到 `min`；返回值恒为安全整数。

2. 三处服务层改用该助手：`page → clampInt(page, 1, 1000000, 1)`、
   `size → clampInt(size, 1, maxSize, 20)`、`limit → clampLimit(limit, max, 默认)`。
   既有上限（500/200/100）与默认值（20/50/20）**全部保持不变**，合法输入结果不变。

3. `routes/review.js` 导出路由同步补下界。

**为什么不用「非法参数返 400」**：本项目既有约定是路径 ID 非法返 400
（`parseIdParam`），而查询型数值参数（`days`/`limit`/`granularity`）一律**静默夹取**。
沿用该约定可保证任何现有前端调用不受影响。

### F-02【P1】`listTransactions` 单页硬上限 50，导致导出被静默截断

**问题现象**

`GET /api/transactions/export` 的注释与路由都写明最多导出 10000 条
（`Math.min(10000, Number(req.query.size) || 1000)`），但实际永远**只导出前 50 条**，
不发任何提示。持有超过 50 条流水的用户点「导出」会拿到一份残缺 CSV。

**根因分析**

导出路由把 `size` 交给 `listTransactions()`，而后者内部有一句与导出语义无关的硬编码
`Math.min(50, ...)`（分页场景「一页」的上限）。两个上限叠乘，较小的 50 生效。
这不是 500，因此不会进错误日志——属于**静默错误结果**，只能靠代码阅读发现。

说明：本次未能用真实数据复现——验证账号 `user_id=3` 的 `transactions` 表为 0 行
（`total=0`），故本项仅由代码实现确认，**未做端到端数据量验证**（见 §五 信息缺失）。

**具体修改措施**

给 `listTransactions()` 增加可选第 4 参数 `maxSize`（默认仍为 `DEFAULT_MAX_SIZE=50`，
分页调用方零改动），导出路由显式传入自己的上限以恢复「导出全量」语义：

```js
// routes/review.js
const EXPORT_MAX_SIZE = 10000;
const size = clampInt(req.query.size, 1, EXPORT_MAX_SIZE, 1000);
const data = await listTransactions(req.userId, 1, size, EXPORT_MAX_SIZE);
```
