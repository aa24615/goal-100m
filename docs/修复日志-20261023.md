## 二、已修复问题

### F1 · 日线落库因单条外键违反导致整批回滚（ERROR 62 条）— 严重

**问题现象**

```
ERROR 日线落库失败  err.message = insert or update on table "stock_daily"
                   violates foreign key constraint "stock_daily_code_fkey"
                   (code 23503)  at async upsertDaily (market.js)
ERROR 收盘结算失败  同因，at async closeSession (market.js)
```
4 分钟内 62 条，且每次失败意味着**该 tick 全部 5576 只标的的日线都没写进去**。

**根因分析**

`market.js` 的内存行情 `state` 在进程启动时由 `SELECT * FROM stocks` 装载；而
`upsertDaily()` 把 `state` 里的全部 code 用**一条** `INSERT ... unnest(...) ON CONFLICT`
批量写入 `stock_daily`。一旦 `state` 中存在 `stocks` 表里已不存在的标的（标的池在进程运行
期间被替换/同步脚本改写，10-22 09:06 前后的真实数据迁移正是如此），Postgres 会对
**整条语句**报 23503 并回滚——一个脏 code 就把其余 5575 个正常标的的日线一起拖没，
且该错误每 5 个 tick 重复一次，形成刷屏。

**涉及文件与代码位置**

- `backend/src/market.js` → `upsertDaily()`（修改后位于第 461 行起）

**具体修改措施**

把未知标的从「致命错误」降级为「可跳过」：在批量插入时 `JOIN stocks`，让陈旧 code 被
静默过滤，其余标的照常落库；再用返回的 `rowCount` 与传入行数比对来发现跳过，并在
**5 分钟节流**下补一条 WARN 列出被跳过的 code（正常路径零额外开销）。

```sql
INSERT INTO stock_daily (...)
SELECT t.* FROM unnest($1..$10)
  AS t(code, seq, trade_date, open, high, low, close, volume, amount, prev_close)
JOIN stocks s ON s.code = t.code          -- ← 新增：过滤未知标的
ON CONFLICT (code, seq) DO UPDATE SET ...
```

**验证结果**

- 数据库对照实验（事务内，已 ROLLBACK）：
  - 加 `JOIN`：`INSERT 0 1`（1 个有效标的写入，2 个幽灵标的跳过，**无报错**）
  - 不加 `JOIN`（原逻辑）：`ERROR: violates foreign key constraint "stock_daily_code_fkey"`
    → **整个事务被中止**，连有效标的 `600519` 也一起丢失 —— 复现了 10-22 的故障模式。
- 现网落库复核：`SELECT seq, trade_date, count(*) FROM stock_daily WHERE seq=(SELECT MAX(seq))`
  → `8658 | 2026-10-23 | 5576`，**全量写入正常，JOIN 未误伤任何标的**。

### F3 · 「请求报文非法(4xx)」误分类业务规则拒绝（WARN 248 条中约 240 条）

**问题现象**

10-22 共 248 条 `请求报文非法(4xx)`，但按 `err.message` 聚合后真实构成是：
`T+1 冻结，当前可卖 0 股`、`可用资金不足`、`邀请码无效`、`剧本不存在`、
`trades 需为数组`、`可选区间为第 1 ~ 4 个交易日` 等 **业务校验失败**，
真正的报文解析失败（`entity.parse.failed`）只是极少数。

**根因分析**

`middleware.js` 的 `errorHandler` 把所有带 `status`(4xx) 的错误一律记为
`请求报文非法(4xx)`。但 `businessError()` / `tradeError()` 构造的是**入参合法、未通过业务校验**
的错误。混用同一文案导致：告警无法区分「客户端把报文打错了」（需排查调用方）与
「用户触发了正常业务边界」（无需处理），4xx 告警事实上失去可行动性。

**涉及文件与代码位置**

- `backend/src/middleware.js` → `errorHandler()`（第 131 行）、`businessError()`（第 157 行）
- `backend/src/services/tradeService.js` → `tradeError()`（第 23 行）

**具体修改措施**

在 `businessError()` / `tradeError()` 上打 `e.business = true` 标记；
`errorHandler` 据此分流为 `业务规则拒绝(4xx)` 与 `请求报文非法(4xx)`。
**响应体与状态码完全不变**，仅日志文案分流。

**验证结果**（现网实测）

| 请求 | HTTP | 日志文案 |
|---|---:|---|
| `POST /api/trade` 资金不足 | 400 | `业务规则拒绝(4xx)` err=可用资金不足 |
| `POST /api/trade` T+1 冻结 | 400 | `业务规则拒绝(4xx)` err=T+1 冻结 |
| `POST /api/login` 畸形 JSON | 400 | `请求报文非法(4xx)` errType=entity.parse.failed |

### F4 · 登录接口只认 `account` 字段，且日志记录空账号造成误导

**问题现象**

```
WARN 登录失败: 参数缺失  {"account":"","ip":"192.168.96.1"}
WARN 请求被拒绝(4xx)     POST /api/login 400  body={"username":"demo","password":"***"}
```
请求体里明明有账号，日志却记 `account:""`，看起来像客户端没传。

**根因分析**

`auth.js` 的 `/login` 只解构 `const { account, password } = req.body`。
仓库内脚本 `backend/gettok.mjs`、`backend/prep.mjs` 以及部分外部调用方按
`{username, password}` 提交，于是拿到误导性的 400。前端 `auth.tsx` 用的是
`account`，所以**线上用户不受影响**，属于接口契约脆弱 + 日志不可自证。

**涉及文件与代码位置**

- `backend/src/auth.js` → `/login`（第 192 行起）

**具体修改措施**

按 `account > username > email` 取值，并在日志中附带 `bodyKeys`
（实际收到的顶层键名），使「参数缺失」类告警可以自证。

**验证结果**

| 用例 | HTTP | 说明 |
|---|---:|---|
| `{"username":"demo","password":"demo123456"}` | **200** | 修复前为 400 |
| `{"account":"demo","password":"demo123456"}` | **200** | 回归，原有路径不变 |
| `{"username":"demo","password":"wrongpass"}` | 401 | 密码错误，符合预期 |
| `{}` | 400 | 真·参数缺失，符合预期 |

### F5 · 前端 WebSocket 连接泄漏（56 次连接 / 40 次断开，净泄漏 16 条）

**问题现象**

`app-2026-10-23.log` 中 WS 连接与断开数量不匹配（56 vs 40）；
`total` 字段单调爬升（00:51:35 起 30 秒内 2→3→4→5→6→7→8），且多条连接之后
**没有任何对应的断开记录**。

**根因分析**

`frontend/src/ws.ts` 的 `connect()` 不是幂等的：页面从后台恢复时，
`visibilitychange` 处理器**直接调用 `connect()` 而不关闭已有连接**，旧连接失去 JS 引用却
仍挂在服务端 `wss.clients` 上，直到心跳超时（60s）才被回收，期间持续累积。
另外 `ws.onerror = () => ws?.close()` 引用的是**模块级变量**而非出错的那个 socket，
并发重建时会误关掉刚建好的新连接，反而触发新的重连。

**涉及文件与代码位置**

- `frontend/src/ws.ts` → `connect()`（第 85 行起）、新增 `reconnectNow()`（第 183 行）、
  `onclose` 4002 分支（第 155 行）、`onerror`（第 173 行）

**具体修改措施**

1. `connect()` **幂等化**：建连前先摘除并关闭仍处于 `CONNECTING/OPEN` 的旧连接
   （`ws.close(4000,'replaced')`），杜绝孤儿连接。
2. `onerror` 改为关闭**局部 `socket`**，不再误伤新连接。
3. 心跳 `setInterval` 内判定改为局部 `socket.readyState`。
4. 抽出统一重建入口 `reconnectNow()`，`visibilitychange` 与导出的 `reconnect()` 共用。
5. 客户端识别服务端新增的 `4002`（见 F6）并**挂起重连让位**，避免两页互挤形成风暴。

**验证结果**

- `npx tsc --noEmit` 通过（0 错误）；`npx vitest run` **41/41 通过**（12 个测试文件）。
- 前端产物重建并部署后，核对容器内 bundle：
  `4002` 命中 1 处、`replaced` 命中 1 处、`4001` 仍命中（原有逻辑未破坏）。

### F6 · 服务端单账号 WS 连接数无上限，断开日志缺诊断字段

**问题现象**：同一 userId 可在短时间内累积 8 条常连接；断开日志只有 `{"total":N}`。

**根因分析**

`index.js` 的 WS 服务未做任何并发限制。客户端泄漏（F5）或被滥用时 `wss.clients`
无上限增长，而每个 tick 都要向**全部**连接广播全市场快照，连接数直接线性放大广播成本。
断开日志只有 `total`，无法区分是客户端正常关闭、鉴权拒绝(4001)、心跳超时还是被限流淘汰。

**涉及文件与代码位置**

- `backend/src/index.js` → `startServer()`：新增 `WS_MAX_PER_USER`（第 160 行）、
  `enforceConnLimit()`（第 163 行）、连接处理（第 205–206 行）、断开日志（第 225 行）

**具体修改措施**

1. 新增单账号连接上限 `WS_MAX_PER_USER`（默认 3，可用环境变量覆盖）：超出时关闭该用户
   **最旧**的几条，保证最近打开的页面可用；未鉴权连接不参与限制。
2. 断开日志补 `userId` / `code` / `reason` / `ms`（存活时长）。

**验证结果**

- 用同一 token 连发 5 条连接 → **存活 3 条**，最旧的 2 条以 `code=4002`
  （`connection limit`）被关闭，与预期完全一致。
- 断开日志实测：
  `{"msg":"WebSocket 客户端断开","ip":"192.168.96.1","userId":21,"code":1005,"reason":"","ms":1525,"total":2}`

## 四、服务启动失败(fatal) 复核（10 条，本轮未再修改）

**现象**：`invalid input syntax for type bigint: "Infinity"`，栈在
`backfillStockShares → loadMarket → main`，导致容器 1 分钟内崩溃重启 10 次。

**根因**：无有效价格时 `marketCap / prevClose` 除零得 `Infinity`，写入 `bigint` 字段被 PG 拒绝。

**现状**：基线提交 `95eb010` 已补上双重保护——`sharesOf()` 内
`Number(prevClose) > 0 ? Number(prevClose) : 10`，`backfillStockShares()` 内
`prev > 0 ? sharesOf(...) : 100000000`。本轮复核确认当前代码**无法再产生 Infinity**，
故不重复修改。现网 10-23 全天 ERROR 为 0，佐证修复有效。
